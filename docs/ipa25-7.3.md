Source investigation, 2026-11-10. LTE remains unaccepted. No modem start,
register access, DMA submission or tablet reboot was performed for this review.

## Confirmed differences

Both downstream `msm8996-v2.dtsi` and `msm8996-v3.dtsi` describe
`qcom,ipa@680000` with `qcom,ipa-hw-ver = <5>`; the UAPI enum maps 5 to
`IPA_HW_v2_5` (and aliases v2.6 to the same value). Their resources include:

| Resource | Downstream value |
|---|---|
| IPA register window | `0x680000`, size `0x4effc` |
| BAM register window | `0x684000`, size `0x26934` |
| IPA / BAM interrupt | GIC SPI 333 / 432 |
| Application execution environment | 0 |
| BAM ownership | `qcom,ipa-bam-remote-mode` |
| Filtering ownership | `qcom,modem-cfg-emb-pipe-flt` |
| DMA allocation constraint | `qcom,use-dma-zone` |

These are source values to reconcile against the exact board/firmware. They
are not instructions to map or write these addresses from userspace.

The downstream IPA v2 driver registers a BAM device with SPS, including remote
management and execution-environment settings (`ipa.c`,
`sps_register_bam_device()`). Its data path uses `sps_transfer_one()` and
`sps_transfer()` (`ipa_dp.c`). Before connecting a pipe on versions through
2.5, `ipa_sps_connect_safe()` normally requests an IPA microcontroller pipe
reset; the comment explicitly describes a hardware limitation when resetting
a BAM pipe during command-queue traffic. Skipping that handshake would discard
an existing hardware workaround.

The current 7.3 driver instead initializes GSI channels unconditionally in
`ipa_probe()`/`ipa_setup()`. Its match table starts with `qcom,msm8998-ipa`
using v3.1 data; its version enum has no 2.5 entry. The mainline BAM DMA driver
exists separately and advertises memory-to-device and device-to-memory
transfers. It is a possible component to evaluate, not a drop-in replacement
for SPS or an already connected IPA transport.

The register programming also differs. Downstream's v2.5 controller reuses
`_ipa_cfg_ep_hdr_v2_0()` and selects a v2.5-specific extended-header/SRAM
implementation in `ipa_utils.c`. Its header register is
`0x170 + 4 * pipe`; mainline v3.1 uses `0x810 + 0x70 * endpoint`.
Adding a compatible string or reusing v3.1 data would select incorrect
register layouts as well as the wrong transport.

QMI control and the network data path are separate. The downstream source
handles IPA modem initialization and filter-rule messages. QRTR enumeration,
SIM detection or successful WDS session establishment would not by themselves
establish that these IPA resources, shared-memory tables or packet pipes work.

## Implementation sequence

1. Establish the exact board resource/ownership contract: clock and interconnect
   votes, BAM execution environment, interrupt routing, DMA address limits,
   IOMMU behavior, shared-memory partitions and modem-owned pipes. Reconcile the
   reference DT with the tablet firmware before adding an enabled node.
2. Design a BAM transport boundary for IPA commands and packet queues. Evaluate
   the existing DMAengine BAM driver's descriptor flags, completion semantics,
   remote ownership and reset behavior against the downstream SPS calls. Keep
   the current GSI path unchanged until equivalent semantics are demonstrated.
3. Implement the v2.5 register, immediate-command, endpoint and SRAM definitions
   from the pinned reference, including microcontroller pipe-reset sequencing.
   Validate layouts against independent reference constants; a build alone is
   insufficient to enable the driver on hardware.
4. Map the modem initialization/filter QMI contract and SSR teardown. Identify
   which side owns each pipe and table; never reset or clear modem-owned state
   based on a v3.x assumption.
5. Use a separate RAM diagnostic with working recovery for incremental resource
   discovery, controller initialization, bounded packet transfer and clean
   shutdown. Preserve the production MSS-disabled configuration throughout.
6. Only then test session setup, bidirectional traffic, reconnect after signal
   loss, SSR and suspend/resume. GNSS and secure-firmware acceptance remain
   prerequisite roadmap gates.

## Audit correction

`tools/audit-t825-lte.py` previously searched for `/ipa` in decompiled DTS.
Ordinary DTS node declarations do not contain that leading slash, so the audit
could falsely report an IPA node absent. It now detects canonical IPA node
declarations, including labeled and downstream `qcom,ipa` names, after `dtc`
normalization. Tests cover enabled, disabled, absent and commented nodes.

The report now calls this `ipa_dt_node_present` and explicitly labels runtime
probing as unobserved. A disabled node still counts as present in the DT;
presence does not prove driver binding. The actual production DT still has no
IPA node after this correction, and its MSS node remains disabled.
